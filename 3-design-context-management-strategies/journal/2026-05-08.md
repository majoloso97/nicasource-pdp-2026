### Journal
I got to this paper from a reference in Chip Huyen's article. It caught my attention because it touches something I've been doing recently: if I need to solve a problem, I first use an AI session as a way to throw off ideas and then when the solution feels complete, I generate a summary + prompt to implement the scaffolding. Empirically, that works very good, and the previous discussion allows me to quickly determine the quality of the generated code.

The core idea is that prompts themselves can be generated and optimized by another LLM. So we remove the human from the loop and instead define prompts as targets that can can be evaluated, ranked and iterated automatically.

A bunch of similarities to machine learing arise: The APE workflow feels very similar to hyperparameter tuning. The model generates multiple candidate instructions, then evaluates and selects the ones with the best performance, like ensemble models. 

I see a potential practical limitation: prompt quality is tied to evaluation quality. This automated prompt generation can run as long as the result of the prompt can be confidently and consistenly evaluated. The paper uses a lot of benchmarks and scores to determine if a generated prompt was better. But, the more flexible the expected result is, the more room to fail there is. Images sound like a particular challenging scenario: how do we evaluate the quality of a generated image? What logical test could we apply? This again hits on the idea that LLM applications are mostly evaluation bound systems.

I also found it interesting that the model generated prompts sometimes outperform human written instructions. The only logic I can derive to this is that LLMs being automated systems can brute force wording that humans would not usually try.

From a systems perspective, this paper highlights an important tradeoff: prompt optimization improves performance, but also introduces operational complexity. Once prompts are generated automatically, having strong observability and evaluation is more important to determine the cause for behavior changes that could be undesired. Also, it becomes more relevant to have version control mechanisms so that rollbacks can be done in a controlled way if a new version breaks existing functionality.

Overall, this paper helped me think about prompts less as static instructions and more as interfaces between models and applications. Many of the implications lie around experimentation loops, where LLMs themselves can be used as an automation tooling instead of only manual iteration.

### Journal
This article was particularly relevant to me because I've been thinking of pgvector less as a "cool add-on" and more as a possible prime mover for moving from MariaDB to PostgreSQL in my current client's stack context. Not only because of vector search itself, but because having vectors and relational data in the same environment feels very attractive for small teams. Specially when most of the application logic already lives in something like Django, where keeping everything close to the ORM can simplify a lot of things.

This blog is pretty explicit about the bottlenecks inherited from PostgreSQL itself: limited indexing options, weaker horizontal scalability, 8KB page constraints for high dimensional embeddings, and fewer vector-native capabilities than dedicated engines. I think having this notion helps to identify under what workload types the system will keep working well enough, and understand what limitations can be worked around and what others are part of the very core of the system.

The benchmarks provided show a promising perspective: The numbers around newer pgvector versions, specially the improvements in build times and the gains from quantization, make it clear that the extension is maturing. If I understood the results correctly, newer releases are not just incremental improvements, but in some scenarios very meaningful jumps in build speed, p99 latency and throughput.

What I found most useful is that this reinforces a distinction I've been feeling in practice: many AI features do not really need vector retrieval as the center of the architecture. In a lot of the things I've built or explored, structured or preprocessed data injected directly into context is more useful than semantic retrieval over a large corpus. In those cases, pgvector being "good enough" as an add-on to a relational system feels more valuable than adopting a separate specialized store too early.

At the same time, the article is a good reminder that "good enough" depends a lot on scale and load patterns. It's one thing for pgvector to work correctly in similarity search tests or in a support chatbot over a moderate corpus. It's another thing entirely to know how it behaves under concurrency, under larger indexes, or when recall targets become stricter. I think this is where the migration decision gets more delicate, because moving databases mostly for vector capabilities is a bigger bet than just enabling an extension.

One thing I keep coming back to is that pgvector probably fits best when vector search is important, but not the entire product. That's very close to my current mental model. If most of the value still comes from normalized data, transactional consistency, joins, existing ORM ergonomics and relatively modest retrieval loads, then keeping vectors in PostgreSQL sounds operationally sensible. The architecture stays simpler, and the vector capability can complement the rest of the system instead of dictating it.

The main red flag, at least to me, is assuming that positive retrieval quality automatically implies production readiness. The article indirectly points to this: recall, p99 latency, build time, memory usage and query throughput are all separate axes. A system can return relevant chunks and still fail operationally if indexing takes too long, if memory pressure gets too high, or if latency collapses once concurrent traffic increases.

Overall, this article helped refine how I think about pgvector adoption. It looks less like a binary "use pgvector" vs "use a vector database" decision, and more like a question of workload shape, scale expectations and operational simplicity. For small teams, and for systems where vector search is supportive rather than the core product, pgvector seems not only viable, but potentially a very pragmatic option. Limits to which pgvector could be stretched without degrading the product's overall quality to are still to be determined with real world evidence in a production environment.
